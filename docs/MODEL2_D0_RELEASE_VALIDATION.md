# Model 2 / Twin 2 D0 release validation

**Gate result:** `D0 CONTRACT VALID`

**Release:** `twin2-d0-debug-v1`

**Scope:** deterministic synthetic debug data only; no model training

## Purpose of D0

D0 is the first immutable Twin 2 data-contract release. It proves that the project can generate, freeze, checksum, load, split, and validate a small structural-state dataset without leaking simulator truth into declared inference inputs.

D0 exists before Model 2 baselines so every later method receives the same audited tensor layout, graph mapping, masks, split assignments, and targets. It is separate from Model 1, Twin 1, Unity navigation, vehicle telemetry, and the historical pre-v0 Model 2 heuristic.

## What D0 may prove

- the release has the required files and machine-readable paths;
- arrays, graph node mappings, dimensions, and masks are internally consistent;
- every scenario belongs to exactly one non-empty scenario-level split;
- required artifacts match their recorded SHA-256 hashes;
- the release can be regenerated byte-for-byte under the recorded configuration/runtime;
- inference inputs exclude `states.npy` and direct hidden-state fields;
- synthetic observed and unobserved component paths both execute;
- the validator fails closed on contract, checksum, split, shape, graph, mask, and leakage errors.

## What D0 does not prove

D0 does not prove Model 2 exists as a trained model, beats a baseline, is proprietary or novel, predicts physical strength, uses calibrated degradation physics, transfers to the ocean, detects real corrosion/cracks, supports deployment, or validates structural safety. Its numerical observations are synthetic Model-1-like proxies, not predictions from a frozen Model 1 checkpoint. Passing D0 authorizes baseline implementation work only.

Model 1 remains **BLOCKED / NOT FROZEN**. D0 does not create Model 1 labels, checkpoints, splits, or training permission.

## Frozen D0 snapshot

The release is stored at `data/model2/d0_debug/` and was built from `configs/model2/d0_debug_release.json` with generator version `oceansense-twin2-d0-release/1.0.0`.

| Property | Frozen value |
| --- | ---: |
| Scenarios | 25 |
| Timesteps per scenario | 4 |
| Nodes per graph | 10 |
| Hidden-state dimensions | 5 |
| Observation dimensions | 6 |
| Train / validation / test | 19 / 2 / 4 |
| Dataset seed | 20260825 |
| `states.npy` shape | `[25, 4, 10, 5]` |
| `observations.npy` shape | `[25, 4, 10, 6]` |
| `observation_mask.npy` shape | `[25, 4, 10]` |

The committed arrays are small debug artifacts (approximately 45 KiB combined). They contain only generated numeric tensors, not raw images, real inspection data, personal data, labels, or model checkpoints. Ground-truth state remains necessary for synthetic loss/evaluation tests but is declared hidden truth and excluded from inference inputs.

## Required files

| File | Role |
| --- | --- |
| `manifest.json` | Release identity, paths, dimensions, layouts, field semantics, inference allowlist, and claim boundary |
| `config.json` or `config.yaml` | Frozen generator and Twin 2 parameters |
| `metadata.json` | Scenario IDs, seed, creation timestamp, generator/runtime/dependencies, synthetic/debug status |
| `splits.json` | Scenario-level, target-independent train/validation/test assignment |
| `structure_graph.json` | One connected graph per scenario, stable component IDs, tensor indices, and valid edges |
| `states.npy` | Simulator-only hidden target tensor `[S,T,N,D_state]` |
| `observations.npy` | Noisy observed-proxy tensor `[S,T,N,D_obs]` |
| `observation_mask.npy` | Boolean/0–1 availability tensor `[S,T,N]` |
| `checksums.json` | SHA-256 inventory for the manifest and every other required artifact |

`checksums.json` cannot hash itself without a circular dependency. It therefore hashes `manifest.json` and all eight other required artifacts; the validator recomputes all eight values.

## Validation checks

`src/oceansense/model2/release_validator.py` checks:

1. required files, exact root paths, safe relative paths, and readable JSON/YAML/NumPy artifacts;
2. manifest dimensions and exact `[scenario,timestep,node,dimension]` layouts;
3. state, observation, and mask shapes against scenario/time/node counts;
4. 0/1 mask values and zero observation vectors where the mask is zero;
5. unique metadata scenario IDs and one graph for every scenario;
6. graph node count, unique/stable IDs, sequential tensor indices, valid edges, and configured connectivity;
7. non-empty train/validation/test splits, no overlap, full coverage, scenario-level unit, split seed, and target-independent assignment basis;
8. SHA-256 syntax and content for every checksummed artifact, including the manifest;
9. an inference-input allowlist that excludes hidden states, targets, and debug truth;
10. observed-proxy declarations that do not use direct hidden-state column names;
11. debug visualization truth marking if optional plots are ever listed;
12. schema/release identity, generation seed, timestamp, generator version, runtime notes, and dependencies;
13. D0-specific synthetic/debug-only status, claim boundary, and exercised observed/unobserved mask states.

Validation is structural and semantic within the declared contract. The `target_independent` split declaration and assignment-basis inspection are auditable controls, not a mathematical proof about arbitrary external generators. Later release builders must also have dedicated split-generation tests.

## Leakage rules

- `states.npy` is permitted only as synthetic training target and controlled evaluation truth.
- Declared inference inputs are exactly `observations.npy`, `observation_mask.npy`, and `structure_graph.json` for D0.
- An observation field may be a named noisy probability/severity proxy, but cannot reuse direct hidden-state names such as `corrosion`, `condition`, `hidden_state`, `true_condition`, or `ground_truth`.
- A numeric zero never means “missing” without the mask; the mask is authoritative.
- Future observations or test-derived statistics must not enter a prediction at an earlier time.
- Ground-truth visualizations must be marked `debug_only` and cannot be inference inputs.
- Split assignment may use scenario ID and seed, not target/state/condition/severity values.

## Checksum and immutability rules

Run the builder only for a new release directory or an explicitly matching D0 release ID. It refuses to replace unknown directories, different release IDs, nested directories, or unexpected files. `--force` is forbidden after a release has been used for a recorded baseline; changes require a new release ID.

Any byte change to config, metadata, split, graph, arrays, or manifest invalidates the stored checksum. Never update a checksum merely to hide an unexplained mutation. Regenerate from the frozen config, compare the entire checksum map, record the cause, and version the release when semantics change.

## CLI usage

Build/reproduce the frozen D0 snapshot:

```powershell
python scripts/build_model2_d0_release.py
```

The command refuses to overwrite the existing release. A controlled pre-baseline reproducibility check may use `--force` only while the release ID and directory contents still match this unconsumed D0 artifact.

Validate strictly as D0:

```powershell
python scripts/validate_model2_release.py `
  --release-dir data/model2/d0_debug `
  --strict `
  --require-debug-d0
```

Write a machine-readable report outside the immutable release:

```powershell
python scripts/validate_model2_release.py `
  --release-dir data/model2/d0_debug `
  --strict `
  --require-debug-d0 `
  --json-out outputs/model2/d0_release_validation.json
```

Strict mode exits nonzero on any failure. The JSON report is evidence about the checked release, not an input artifact and not a Model 2 metric.

## Split rules

All 25 scenario IDs are assigned by a fixed SHA-256 scenario-ID bucket function using the recorded seed/config. No timestep, node, hidden state, label, or severity determines the split. Every scenario is wholly contained in one split; train, validation, and test are non-empty and disjoint.

D0 scenario separation is sufficient for a debug contract. An S1 comparison release must additionally separate asset/template lineage, near-duplicate generations, parameter families, and predeclared out-of-distribution regimes as specified in `docs/MODEL2_BASELINE_COMPARISON_PLAN.md`.

## Gate evidence and next step

The frozen D0 release passed strict validation with eight checksums verified, connected graph mappings, both mask states exercised, and split counts 19/2/4. Unit tests independently inject missing files, checksum corruption, overlapping/missing splits, shape errors, mask errors, graph mismatch, and hidden-state leakage; all are rejected.

The next step is to define and implement a common baseline loader/evaluator against this immutable D0 contract, starting with Last Observation and Simple Heuristic smoke baselines. D0 may be used to debug those code paths. Any reported comparison or training claim requires a separately reviewed S1 synthetic release and the complete six-baseline protocol; no Model 2 superiority claim is currently allowed.
